# 1. Mapping Summary

The narrow repository review found that `notification-service` targets **.NET 8** and references `Npgsql.EntityFrameworkCore.PostgreSQL` **8.0.4**, `Microsoft.EntityFrameworkCore.Design` **8.0.4**, and `EFCore.NamingConventions` 8.0.3. It uses explicit Fluent mapping with `UseNpgsql`. That is compatible with the proposed `ai-available-service` Code First plan. This service should use explicit snake_case Fluent mappings and EF Core Migrations; it must not copy `EnsureCreated`, connection-string fallbacks/secrets, or unrelated notification infrastructure.

| Decision | Plan |
|---|---|
| Core entity/table count | Four: `AiProduct`, `ProductAsset`, `ProductPurchase`, `ProductRating`. |
| Provider / physical database | Npgsql EF Core 8.x against PostgreSQL database `ai_available`. |
| Enum strategy | PostgreSQL native enum types, registered through the Npgsql 8 data source and declared in the EF model, with explicit `PgName` member labels rather than implicit name translation. |
| UUID strategy | Application-generated `Guid` values, configured as non-store-generated. This makes `ProductPurchase.Id` available before the payment request and removes the need for `pgcrypto`. |
| Arrays | `string[]` mapped natively to PostgreSQL `text[]`; no JSONB or join tables. |
| Trigger strategy | Retain exactly one small cross-row integrity trigger: block `ProductAsset` insert/update/delete after the parent Product has a non-null `first_published_at`. All other candidate triggers become service-layer workflow rules. |
| Concurrency strategy | No `row_version`/`xmin` mapping in the initial model. Explicit database transactions, deterministic row locks, and unique constraints are sufficient for the identified MVP commands. |
| Timestamp strategy | `DateTimeOffset`, UTC values set by application commands. Creation defaults remain a database safety fallback only; the application does not rely on hidden timestamp behavior. |

The approved Phase 3 revisions are incorporated exactly: whole-VND price without a divisibility-by-10 rule, rounded platform fee, no preview-object Purchase snapshot, unique protected storage objects, service-enforced Published editing restriction, and a successful-purchases-only history index.

## Array mapping decision

Use `string[]`, not `List<string>`, for `Technologies` and `AiCapabilities`.

- Npgsql maps `string[]` directly and idiomatically to PostgreSQL `text[]`; no converter or JSON serialization is necessary.
- `string[]` accurately communicates the persisted value shape. `List<string>` is a mutable UI/domain collection abstraction, not a better database mapping for an array column.
- Domain update methods should normalize and replace the entire array (for example, a newly built distinct trimmed array) rather than mutate an array in place. This makes the intended EF change visible and centralizes de-duplication/nonblank validation in the service/domain command.
- The arrays are initialized to `Array.Empty<string>()`, then mapped with `ARRAY[]::text[]` as their database default. They remain display/write metadata, not searchable normalized relationships.

# 4. Navigation & Relationship Mapping

Only the relationships below are mapped. Identity and Payment values remain scalar columns; there are no external `DbSet`s, entity types, navigations, or foreign keys.

| Principal -> Dependent | Cardinality / navigation | FK | Fluent relationship | Delete behavior |
|---|---|---|---|---|
| `AiProduct` -> `ProductAsset` | One Product has zero-to-many `Assets`; each Asset has one required `Product`. | `ProductAsset.ProductId` | `HasOne(x => x.Product).WithMany(x => x.Assets).HasForeignKey(x => x.ProductId)` | `DeleteBehavior.Cascade` / `ON DELETE CASCADE`. The service permits product deletion only for a never-published Draft, so its Draft assets are removed with it. |
| `AiProduct` -> `ProductPurchase` | One Product has zero-to-many `Purchases`; each Purchase has one required `Product`. | `ProductPurchase.ProductId` | `HasOne(x => x.Product).WithMany(x => x.Purchases).HasForeignKey(x => x.ProductId)` | `DeleteBehavior.Restrict` / `ON DELETE RESTRICT`. Purchase history prevents Product deletion. |
| `ProductPurchase` -> `ProductRating` | One Purchase has zero-or-one `Rating`; each Rating has one required `Purchase`. | `ProductRating.PurchaseId` | `HasOne(x => x.Purchase).WithOne(x => x.Rating).HasForeignKey<ProductRating>(x => x.PurchaseId)` | `DeleteBehavior.Restrict` / `ON DELETE RESTRICT`. The Client hard-deletes the Rating, never the successful Purchase. |

`ProductPurchase` and `ProductRating` should not configure `AiProduct`/buyer navigations from any external UUID. In particular, `SellerExpertId`, `BuyerClientId`, `SellerExpertIdAtPurchase`, and `PaymentTransactionId` are scalar-only properties.

# 5. Enum Mapping Decision

## Chosen strategy: PostgreSQL native enums

Use conventional PascalCase C# members and map them to named PostgreSQL types with **explicit uppercase `PgName` labels**. No enum label may depend on Npgsql's default snake-case naming translator.

| C# enum | PostgreSQL native type | Explicit CLR member -> PostgreSQL label mapping |
|---|---|---|
| `ProductStatus` | `product_status` | `Draft -> DRAFT`; `Published -> PUBLISHED`; `Unpublished -> UNPUBLISHED` |
| `ProductAssetType` | `product_asset_type` | `SourceCode -> SOURCE_CODE`; `Video -> VIDEO`; `Dataset -> DATASET`; `Document -> DOCUMENT` |
| `PreviewType` | `preview_type` | `Image -> IMAGE`; `Video -> VIDEO` |
| `PurchaseStatus` | `purchase_status` | `PendingPayment -> PENDING_PAYMENT`; `Success -> SUCCESS` |

Future enum member declarations use the Npgsql-supported `PgName` attribute on **every** member, for example conceptually `ProductStatus.Draft` has `PgName("DRAFT")`. The same explicit annotations apply to the complete mapping above. The attributes are the deterministic CLR-member-to-label policy; they preserve .NET member naming while the physical schema retains its approved uppercase labels.

### Why native enums rather than a text/varchar conversion

| Option | Assessment |
|---|---|
| Native PostgreSQL enum | **Chosen.** The approved ERD already names physical enum types. The provider supports them, database values remain self-describing/constrained, and migration-generated types prevent arbitrary status strings. This is clear for SQL operators and aligns with the small, stable domains. |
| `text`/`varchar` conversion | Not chosen. It would make enum data readable but would weaken the physical ERD unless every column also received a duplicated `CHECK`; it provides no advantage for these small known domains. |

For **Npgsql.EntityFrameworkCore.PostgreSQL 8.0.4 / EF Core 8.0.4**, configure the lower-level mapping through one `NpgsqlDataSourceBuilder`: call `MapEnum<TEnum>(pgName: "...")` for each of the four exact type names, build that data source, then pass it to `UseNpgsql`. In `OnModelCreating`, declare the same four enum types with `HasPostgresEnum<TEnum>(schema: "public", name: "...")` so EF migrations create the physical types. The `PgName` member attributes above are honored by this Npgsql 8 mapping/model path and define the exact labels.

Do **not** use the EF Core 9-style `UseNpgsql(..., o => o.MapEnum<TEnum>(...))` shortcut in the future .NET 8 service. Do not use a global/static type mapper either. The generated initial migration and its SQL must be explicitly reviewed to confirm the four PostgreSQL types contain the exact uppercase labels above; every CHECK and partial-index filter must continue to use those physical labels (for example, `'PUBLISHED'` and `'SUCCESS'`).

When adding an enum value later, create a dedicated forward-only EF migration that issues PostgreSQL's enum-value addition through Npgsql's migration support. PostgreSQL enum value removal/reordering is not routine rollback material; do not alter values casually.

# 6. AiProductConfiguration Plan

`AiProductConfiguration` maps `AiProduct` to `ai_product` with `pk_ai_product` on `id`.

## Columns and defaults

- Map every property in the `AiProduct` table above to its explicit snake_case column name.
- Configure `id` as `uuid`, key, `ValueGeneratedNever`; no `gen_random_uuid()` default is emitted.
- Map external UUID references as plain `uuid` properties and external codes as required `text` properties. Do not configure relationships for them.
- Map `name`, `description`, and `category_code` to `text`; do not invent arbitrary varchar limits.
- Require `name`, `category_code`, and `price_vnd` for Draft creation as well as at the database level. Draft creation may leave `description` null, omit the whole preview group, and omit any/all protected assets; Publish separately validates the missing Description and all four assets.
- Map `technologies` and `ai_capabilities` to `text[]`, required, with `ARRAY[]::text[]` defaults.
- Map `price_vnd` as required `numeric(19,2)` with explicit precision `(19, 2)`.
- Map `status` as required native `product_status`, default `DRAFT`.
- Map publication and ordinary timestamps as `timestamptz`. `created_at` and `updated_at` have `now()` insert defaults as database safety fallbacks; application commands set their UTC values explicitly.
- Map optional preview metadata to nullable `text`, `bigint`, `numeric(8,3)`, `timestamptz`, and nullable native `preview_type`, respectively.

## Constraints

The migration creates the named checks listed in section 10:

- `ck_ai_product_name_nonblank`
- `ck_ai_product_category_code_nonblank`
- `ck_ai_product_description_nonblank_if_present`
- `ck_ai_product_price_vnd_positive_whole`
- `ck_ai_product_preview_shape`
- `ck_ai_product_publication_timestamp_shape`

The preview check is intentionally one readable table-level constraint: all preview values are null when there is no preview; otherwise common storage metadata is complete, byte size is nonnegative, and only a video has a duration in `(0, 240]`.

## Indexes

- `ix_ai_product_published_recent`: `last_published_at DESC, id`, filtered to `status = 'PUBLISHED'`.
- `ix_ai_product_published_category_price`: `category_code, price_vnd, id`, filtered to `status = 'PUBLISHED'`.
- `ix_ai_product_published_price`: `price_vnd, id`, filtered to `status = 'PUBLISHED'`.
- `ix_ai_product_seller_updated`: `seller_expert_id, updated_at DESC, id`.

No full-text, trigram, technology, or capability index is created for MVP.

# 8. ProductPurchaseConfiguration Plan

`ProductPurchaseConfiguration` maps `ProductPurchase` to `product_purchase` with `pk_product_purchase` on `id`.

## Columns and relationship

- Map `id` as application-generated `uuid`, key, and `ValueGeneratedNever`. The command/factory creates it before the initial pending Purchase is persisted or payment is called.
- Map `product_id` as required `uuid` FK, with `DeleteBehavior.Restrict` / `ON DELETE RESTRICT`.
- Map `buyer_client_id`, `buyer_client_code`, seller snapshots, and `payment_transaction_id` as scalar columns only; `payment_transaction_id` is nullable `uuid` and not a Payment FK.
- Map `status` to required native `purchase_status` with default `PENDING_PAYMENT`.
- Map all successful-snapshot strings and UUIDs as nullable because a pending intent must have no snapshot. Do not map preview bucket/object snapshot columns.
- Map each monetary snapshot as nullable `numeric(19,2)` with explicit precision `(19, 2)`.
- Map success/entitlement timestamps as nullable `timestamptz`; map `created_at`/`updated_at` as required `timestamptz` with `now()` insert fallbacks.
- Configure the optional inverse one-to-one `Rating` navigation in `ProductRatingConfiguration`; do not add a `rating_id` column here.

## Constraints and indexes

- `uq_product_purchase_product_buyer`: unique constraint on `(product_id, buyer_client_id)`, regardless of status. It is the stable intent/ownership uniqueness rule.
- `uq_product_purchase_payment_transaction`: unique constraint on nullable `payment_transaction_id`. PostgreSQL permits multiple nulls, while a successful payment reference can attach to only one Purchase.
- `ck_product_purchase_status_snapshot_shape`: PENDING rows have all success-only payment/snapshot/entitlement fields null; SUCCESS rows have all required fields non-null.
- `ck_product_purchase_success_monetary_entitlement`: successful values are whole VND, platform fee is `round(price_vnd_at_purchase * 0.10, 0)`, Expert net equals price minus fee, and access expiration is 30 days after success time.
- `ix_product_purchase_buyer_history`: `(buyer_client_id, purchased_at DESC, id)` filtered to `status = 'SUCCESS'`. It serves Purchase History only; a direct entitlement lookup is served by the Product/Buyer unique constraint.

The purchase configuration does not attempt to make a Payment transaction an internal EF principal. Payment execution and retry behavior remain service-workflow concerns.

# 10. Check Constraints

The following are scalar row-shape constraints suitable for migration-generated PostgreSQL `CHECK`s. SQL uses physical snake_case names and PostgreSQL's native enum literals.

| Constraint Name | Table | SQL / Semantic Rule | Why DB-level |
|---|---|---|---|
| `ck_ai_product_name_nonblank` | `ai_product` | `btrim(name) <> ''` | Required scalar field cannot be bypassed with whitespace. |
| `ck_ai_product_category_code_nonblank` | `ai_product` | `btrim(category_code) <> ''` | Category code is required even though its vocabulary is application-owned. |
| `ck_ai_product_description_nonblank_if_present` | `ai_product` | `description IS NULL OR btrim(description) <> ''` | Draft may omit description, but may not persist a meaningless non-null value. |
| `ck_ai_product_price_vnd_positive_whole` | `ai_product` | `price_vnd > 0 AND price_vnd = trunc(price_vnd)` | Preserves positive whole-VND semantics; intentionally contains no modulo/divisibility rule. |
| `ck_ai_product_preview_shape` | `ai_product` | Either all preview columns are null, or type/bucket/key/original filename/content type/byte size/upload time are non-null and `preview_byte_size >= 0`; `IMAGE` requires duration null, while `VIDEO` requires `preview_video_duration_seconds > 0 AND <= 240.000`. | One optional preview column group needs a durable all-or-none shape. |
| `ck_ai_product_publication_timestamp_shape` | `ai_product` | `DRAFT` has both publication timestamps null; `PUBLISHED`/`UNPUBLISHED` have both non-null and `last_published_at >= first_published_at`. | Preserves a coherent persisted lifecycle shape without trying to encode transition history. |
| `ck_product_asset_byte_size_nonnegative` | `product_asset` | `byte_size >= 0` | Raw byte counts cannot be negative. |
| `ck_product_purchase_status_snapshot_shape` | `product_purchase` | `PENDING_PAYMENT` requires payment transaction ID, all success snapshot fields, `purchased_at`, and `access_expires_at` to be null; `SUCCESS` requires every one of those fields to be non-null. | Prevents a pending intent from accidentally looking like ownership and prevents incomplete history. |
| `ck_product_purchase_success_monetary_entitlement` | `product_purchase` | For `SUCCESS`: each gross/fee/net amount equals `trunc(amount)`; `platform_fee_vnd_at_purchase = round(price_vnd_at_purchase * 0.10, 0)`; `expert_net_vnd_at_purchase = price_vnd_at_purchase - platform_fee_vnd_at_purchase`; and `access_expires_at = purchased_at + interval '30 days'`. | The financial snapshot and entitlement are row-local, deterministic facts. |
| `ck_product_rating_score_range` | `product_rating` | `score BETWEEN 1 AND 5` | Stable bounded rating domain. |
| `ck_product_rating_review_text_nonblank_if_present` | `product_rating` | `review_text IS NULL OR btrim(review_text) <> ''` | Avoids an empty review distinct from no review. |

Checks intentionally do **not** encode current caller identity, Identity role, previous status, four-asset aggregate count, full Product column immutability while Published, or a remote Payment result. Those are workflow/cross-row concerns and belong below.

# 11. Workflow Rules Kept in Service Layer

The future service uses command-oriented transactions. State-changing commands lock the `ai_product` row before reading/changing its state. Purchase commands use a deterministic lock order (`ai_product`, then `product_purchase` when it exists) to reduce deadlock risk. The remote payment call requires the stable Purchase ID for idempotent reconciliation; a database transaction does not make the remote service transactional.

| Rule | Why Service Layer | Transaction / Lock Requirement |
|---|---|---|
| Authenticate current user; verify CLIENT/EXPERT role/status | Identity owns user role and status. | Identity lookup plus normal command transaction as needed. |
| Create Draft / update Product only for seller | Draft creation requires Name + Category + positive whole-VND Price; external actor ownership applies to updates. Description, preview, and protected assets remain optional/incomplete only in Draft. | Validate the three Draft-required values before insert; lock Product before seller/state check for an existing Product. |
| Allowed lifecycle command transitions | Requires previous status and command intent; a native enum/check cannot express authorized actor/action. | Lock Product row; reject invalid source status; set publication timestamps atomically. |
| Hard-delete only seller-owned never-published Draft | Requires actor ownership and lifecycle command policy. | Lock Product; verify `DRAFT` and null `FirstPublishedAt`; delete in same transaction. Asset cascade removes Draft assets. |
| Validate description and exactly four distinct assets before Publish | Aggregate query across `product_asset` rows and Product command rules. | Lock Product, read/validate required asset types in same transaction, then Publish. |
| Prevent basic metadata/price/preview edits while Published | This is a command/workflow rule over many Product columns; a broad trigger would be fragile. | Lock Product; permit change only in Draft or Unpublished. |
| Verify Supabase upload ownership, MIME/media facts, and preview duration | DB validates stored shape, but cannot prove the browser/user owns the object or inspect bytes safely. | Validate before metadata command; lock Product before associating/replacing metadata. |
| Product asset Draft replace/remove flow | User ownership/state and storage cleanup are external workflow concerns. | Lock parent Product before Asset operation; retained asset trigger supplies a final cross-row guard. |
| Client purchase eligibility and current Product purchasability | Role, self-purchase, current status, and identity values are external/current facts. | Lock Product and pending Purchase; revalidate immediately before settlement. |
| Stable intent creation and retry behavior | Requires returning existing pending intent rather than creating attempts, and later remote-payment reconciliation. | Insert under transaction; rely on unique conflict handling/reload. Retry locks existing Purchase and Product. |
| Current-price snapshot and rounded fee assignment at SUCCESS | Needs current locked Product value and payment-service result. | Lock Product/Purchase; calculate `decimal.Round(price * 0.10m, 0, MidpointRounding.AwayFromZero)` so positive `.5` VND values match PostgreSQL `round(numeric, 0)`, then persist the terminal snapshot. |
| Successful snapshot immutability | The service exposes no update command for `SUCCESS` Purchase snapshot/status fields. | Transition only `PENDING_PAYMENT -> SUCCESS` in a transaction; later writes are rejected. |
| Protected download authorization | Depends on authenticated caller, requested object, current instant, and signed-access provider. | Read Purchase by Product/Buyer; require `SUCCESS` and `AccessExpiresAt > UtcNow`. |
| Rating eligibility, edit, and delete authorization | Depends on current Client being the Purchase buyer. | Query/lock Purchase and Rating as appropriate; database unique constraint resolves duplicate create races. |
| Normalize technology/capability arrays and validate category vocabulary | These are application data-quality/taxonomy rules, not tables. | Ordinary Product update transaction. |

# 12. Trigger Decision

The approved outcomes remain enforced, but this mapping deliberately avoids a trigger-heavy database. The retained trigger covers the only high-value cross-row invariant that could otherwise be bypassed after first publish.

| Candidate | Decision | Reason |
|---|---|---|
| 1. Product lifecycle transition validation | SERVICE ONLY | A command handler under a Product row lock is clearer than trigger logic and can enforce owner/role/action semantics. The DB retains enum and timestamp-shape checks. |
| 2. Product hard-delete only while never-published Draft | SERVICE ONLY | Actor authorization is essential and only the service has it. Purchase FK restriction and asset cascade already protect physical referential behavior. |
| 3. Verify four assets before Publish | SERVICE ONLY | It is an aggregate validation naturally performed in the Publish transaction; a trigger would duplicate a business command and complicate asset/write ordering. |
| 4. ProductAsset mutation after first Publish | **KEEP AS DB TRIGGER** | It is a small, durable, high-value cross-row integrity rule. It prevents accidental/direct DML from changing locked deliverables even after Unpublish, without governing broad Product edits. |
| 5. Successful Purchase snapshot immutability | SERVICE ONLY | The service provides only a single pending-to-success terminal transition; DB checks guarantee shape/consistency. A trigger would add broad column-comparison maintenance for a command that the repository need not expose. |
| 6. Rating only when Purchase is SUCCESS | SERVICE ONLY | Rating ownership/authorization already requires the service to resolve the Purchase/current Client. The service checks terminal status before insert; unique FK relation guarantees one rating. |

## Retained trigger design

| Item | Future design |
|---|---|
| Function name | `fn_reject_product_asset_mutation_after_first_publish()` |
| Trigger name | `trg_product_asset_lock_after_first_publish` |
| Table/timing/events | `BEFORE INSERT OR UPDATE OR DELETE ON product_asset FOR EACH ROW` |
| Responsibility | Determine the relevant parent Product ID(s): `NEW.product_id` for INSERT, `OLD.product_id` and `NEW.product_id` for UPDATE, and `OLD.product_id` for DELETE. Lock/read those parent rows in deterministic UUID order. Raise a PostgreSQL exception if any has non-null `first_published_at`. |
| Why UPDATE checks both parents | It blocks modifying an existing locked asset and blocks moving an asset either out of or into a locked Product if future code attempted a ProductId change. |
| What it does not do | It does not validate caller ownership, asset completeness, transition state, MIME type, or storage cleanup. Those remain service concerns. |
| Initial migration Up | After `ai_product` and `product_asset` exist, use `migrationBuilder.Sql(...)` to create the PL/pgSQL function, then the named trigger. It remains versioned as EF migration content, not a manually applied schema script. |
| Initial migration Down | Drop the named trigger first, then drop the named function, before the related tables are removed. A later migration replacing it must similarly drop/recreate both deterministically. |

# 14. Timestamp & UUID Strategy

## Timestamps

Use `DateTimeOffset` for every PostgreSQL `timestamptz` column. It models an instant with offset rather than a timezone-less wall-clock value, works cleanly with Npgsql `timestamptz`, and lets the service consistently write `DateTimeOffset.UtcNow`.

| Field(s) | Setter / rule |
|---|---|
| `CreatedAt` | Set by application when the entity/intent is created. `now()` default is an insert-only fallback, not an application clock source. |
| `UpdatedAt` | Set by the service for each permitted update/terminal transition. There is no database `ON UPDATE` trigger. |
| `UploadedAt` / `PreviewUploadedAt` | Set by the service when validated upload metadata is accepted/replaced. |
| `FirstPublishedAt` | Set once by the Publish command using one captured UTC `now`; never cleared. |
| `LastPublishedAt` | Set by each Publish/Republish command using that command's UTC `now`. |
| `PurchasedAt` | Set when the locked pending Purchase becomes `SUCCESS` after correlated payment success. |
| `AccessExpiresAt` | Calculated by application as `PurchasedAt.AddDays(30)` in the same success transition; DB check verifies it. |

Incoming API values never set lifecycle, purchase, or audit timestamps directly. Database time may differ slightly from app time, but application-set values make a command's linked fields (`PurchasedAt` and expiry, or both publish timestamps) deterministic.

## UUIDs

Generate all four entity IDs in application code (for example, an entity factory assigns `Guid.NewGuid()` before tracking). Configure each ID as `ValueGeneratedNever`; do not emit `gen_random_uuid()` defaults or install `pgcrypto` solely for this service.

This is especially necessary for `ProductPurchase.Id`: the first pending row's ID exists before the payment-service settlement request and is the future idempotency/correlation reference. The UUIDv4 generation quality supplied by .NET is adequate for this MVP; its values are opaque IDs, not time/order values.

# 15. Concurrency Strategy

**Choice: A — normal transactions, explicit row locks, and unique constraints are sufficient for the initial MVP. Do not add `row_version`, SQL Server-style rowversion, or a PostgreSQL `xmin` mapping.** This preserves the approved ERD and targets the actual race conditions rather than adding a generic token.

| Risk | Chosen control |
|---|---|
| Two Product metadata updates | Update command locks/reloads the Product before checking status and applying one command. Published edits are rejected after the locked state read. |
| Publish vs asset replacement/removal | Both commands lock the parent Product before changing data. Publish checks the asset set under that transaction; the retained trigger is a final guard against post-first-publish asset DML. |
| Duplicate Client/Product purchase request | `uq_product_purchase_product_buyer` is authoritative. Service handles unique-conflict/reload and returns the stable pending row. |
| Concurrent payment retry/callback | Lock the Purchase and Product in deterministic order; accept one pending-to-success transition and use `ProductPurchase.Id` with payment-service idempotency/reconciliation. |
| Concurrent rating create/edit | `uq_product_rating_purchase` resolves duplicate creates; edit/delete loads the caller-owned Rating/Purchase within its command transaction. |

An optimistic token would not solve the remote payment boundary or replace the required unique constraint. It would also require callers to handle concurrency exceptions on ordinary commands. Revisit `xmin` only if later product-edit traffic demonstrates lock contention or a genuine disconnected-edit requirement.

# 16. Initial Migration Blueprint

The initial migration is generated from the future DbContext and reviewed before application. It is the only permitted schema-creation path.

## Creation order

1. Ensure the target database is `ai_available`; no cross-service schema/FK is created.
2. Create native PostgreSQL enum types: `product_status`, `product_asset_type`, `preview_type`, `purchase_status`.
3. Create `ai_product` with its scalar columns, text-array defaults, `numeric(19,2)`/`numeric(8,3)` mappings, timestamp defaults, primary key, checks, and Product indexes.
4. Create `product_asset` with its FK to `ai_product` using `ON DELETE CASCADE`, byte-size check, and both unique constraints.
5. Create `product_purchase` with its FK to `ai_product` using `ON DELETE RESTRICT`, status/snapshot/monetary/entitlement checks, unique constraints, and successful-history partial index.
6. Create `product_rating` with its FK to `product_purchase` using `ON DELETE RESTRICT`, score/review checks, and unique constraint.
7. Create `fn_reject_product_asset_mutation_after_first_publish()` and `trg_product_asset_lock_after_first_publish` using versioned `migrationBuilder.Sql` operations.
8. Verify generated SQL names, native enum declarations, partial-index filters, default literals, check syntax, and trigger function/rollback SQL in a disposable PostgreSQL test database during the later implementation phase.

## Rollback order

1. Drop `trg_product_asset_lock_after_first_publish`.
2. Drop `fn_reject_product_asset_mutation_after_first_publish()`.
3. Drop `product_rating`.
4. Drop `product_purchase`.
5. Drop `product_asset`.
6. Drop `ai_product`.
7. Drop the four enum types after all dependent columns/tables are gone.

`Database.EnsureCreated()` is explicitly prohibited. Development and production schema changes use **EF Core Migrations** (`Add-Migration`/`dotnet ef migrations add`, review, then `database update` or the approved deployment migration runner), never an automatic EnsureCreated path.
